# Agentic本地知识库搜索工具

基于 ripgrep 和大语言模型的搜索本地文本的搜索工具。

## 功能特点

- 🚀 使用 ripgrep 实现毫秒级规范全文检索
      只要大语言模型生成的关键词足够好，最后的成功率是大于向量搜索的。
      速度其实和向量差不多并且还不用提前生成向量。
      整体思路是把 opencode 回答问题的关键部分摘出来了。
- 🧠 快慢模型分离架构：快速模型生成正则，推理模型做智能初筛和最终分析
- 🔄 正则生成自我修复：自动检测语法错误并重试优化
- 🎯 Agentic 智能初筛：推理模型自动筛选最相关的 5-8 个结果，减少噪音
- 📖 四阶段处理流程：正则生成 → 搜索 → 智能初筛 → 精准扩展上下文
- 🎯 智能目录路由：agentic_search 通过目录直接定位章节，自动配对条文解释，准确度极高
- 💬 流式输出，实时展示 AI 分析结果
- 🤖 原生 Agent 架构 (V5)：抛弃过度工程化的人工规则，回归原生 ReAct 范式，为大模型提供原子化工具（Grep搜索、精准翻页），让大模型自主接管逻辑与调度。
- 💰 极低 Token 消耗 (V5相比V4)：通过全文件目录的“零成本初筛”替代昂贵且主观的“大模型打分制”，既保留了完整上下文，又大幅降低了 API 成本。

## 安装步骤

### 1. 环境要求

- Python 3.8+
- Windows 操作系统（请下载对应系统的rg.exe，windows系统用当前文件夹的即可）

### 2. 安装依赖

```cmd
pip install openai python-dotenv
```

或使用 uv（推荐）：

```cmd
uv pip install openai python-dotenv
```

### 3. 准备规范文件

将建筑规范文本文件（.txt 格式）放入 `specs/` 文件夹中。项目已包含以下规范：

- 建筑结构荷载规范
- 建筑抗震设计规范
- 建筑地基基础设计规范
- 混凝土结构设计规范
- 钢结构设计标准
- 砌体结构设计规范
- 高层建筑混凝土结构技术规程
- 建筑地基处理技术规范
- 建筑桩基技术规范
- 门式刚架轻型房屋钢结构技术规范

### 4. 配置 API Key

复制 `.env.example` 为 `.env`：

```cmd
copy .env.example .env
```

编辑 `.env` 文件，填入你的 ModelScope API Key：

```env
# ModelScope API 配置
MODELSCOPE_API_KEY=your-api-key-here

# 模型配置（可选，默认使用 Kimi-K2.5）
# MODEL_NAME=moonshotai/Kimi-K2.5
# MODEL_NAME=Qwen/Qwen3-235B-A22B-Instruct-2507
```

支持的模型：
- `moonshotai/Kimi-K2.5`（默认推理模型，强推理能力）
- `Qwen/Qwen3-235B-A22B-Instruct-2507`（千亿参数推理模型，推理能力强）
- `Qwen/Qwen3-30B-A3B-Instruct-2507`（快速模型，用于正则生成）

注意：V2 版本中，智能初筛和最终分析都使用推理模型（Kimi/Qwen-235B），只有正则生成使用快速模型（Qwen-30B）。

## 使用方法

### 版本说明

项目提供四个版本，每个版本在前一版本基础上逐步优化：

**V1 - 基础版本（rg_search_v1.py）**
- 单模型处理所有任务
- 正则生成 → ripgrep 检索 → 全量上下文扩展 → AI 综合回答
- 适用场景：快速验证概念，简单查询

**V2 - 通用优化版本（rg_search_v2.py）**
- 核心升级：
  - 快慢模型分离：快速模型生成正则，推理模型做智能初筛和最终分析
  - 正则生成自我修复：自动检测语法错误并重试优化（最多 3 次）
  - Agentic 智能初筛：推理模型自动筛选最相关的 5-8 个结果，减少噪音
- 工作流程：生成正则（带自我修复）→ 搜索 → 智能初筛 → 精准扩展上下文 → 回答
- 适用场景：通用文本库，问题答案集中在单个条文段落中

**V3 - Agentic 循环搜索版本（rg_search_v3.py）**
- 核心升级：
  1. 混合智能展卷（SmartExpander）
     - 规则引擎优先：使用正则快速测边界（识别标题、条款编号等）
     - LLM 语义兜底：遇到以下情况自动触发大模型语义提取
       - 达到最大搜索半径仍未找到边界（长文本无规则）
       - 检测到表格引用但未捕获表格内容（如"见下表"但没有 `|` 符号）
       - 提取文本过短（可能是孤立标题）
       - 文本过长且缺乏结构化标记
  2. Agentic 循环搜索（多轮迭代）
     - 智能评估：每轮搜索后，推理模型判断信息是否足够回答问题
     - 外部引用检测：识别"见表 5.2.1"、"按第 6.1.2 条执行"等嵌套引用陷阱
     - 动态策略调整：根据缺失信息（`missing_info`）重新生成搜索策略
     - 防死循环机制：记录历史查询，避免重复搜索；最多迭代 3 轮
- 适用场景：复杂查询，涉及多表格、多条文交叉引用

**V4 - 打分制优化版本（rg_search_v4.py）**
- 核心升级：
  1. 打分制筛选（0-10 分）
     - 9-10 分：直接回答问题的核心条文
     - 7-8 分：相关且提供关键信息
     - 4-6 分：弱相关或背景信息
     - 0-3 分：不相关或误匹配（自动加入垃圾池）
  2. 三池分流策略
     - 精选池：已展卷的高质量锚点
     - 垃圾池：<3 分的不相关锚点
     - 候选池：待定锚点（3-6 分或降级的 7 分）
  3. 动态截断机制
     - 7-8 分总数 ≤8：全部展卷
     - 7-8 分总数 >8：7 分降级到候选池
     - 不足 5 条时从候选池智能补充
  4. 二次循环检查
     - 即使评估为"信息完整"，若候选池有 ≥5 分锚点或精选池 <2 条，强制进入下一轮
  5. 场景分类策略
     - 跳转查表：检测到表格号或条文号引用
     - 放宽搜索：锚点太少（<5 条）
     - 换词精搜：锚点足够但信息不完整
- 适用场景：最复杂的查询，需要精准控制信息质量和召回率

**V5 - 原生 Agent 极简版本（rg_search_v5.py）🚀 终极推荐**
- 核心升级（从过度工程化回归大道至简）：
  1. 彻底废弃人为设定的流水线（如正则生成、V4的打分/精选池/垃圾池分流）。
  2. 原生 Function Calling：将系统抽象为仅存两个健壮的原子工具（`execute_grep` 搜索、`read_file_range` 翻页阅读）。
  3. LLM 自主调度 (ReAct 范式)：直接把完整的规范文件目录交给大模型，大模型凭借强大的世界知识，自主决定去哪个文件搜、搜什么词。
  4. 零成本降维过滤：当用户提问时，模型瞬间判断目标文件并利用 `include_files` 参数实现毫秒级精准过滤，跳过繁琐低效的文本打分。
- **与 V4 的效果比对（为何 V5 远胜 V4）：**
  - **V4 的痛点（极自以为是）**：强迫大模型对碎片文本进行“0-10绝对量化打分”，不仅消耗海量 Token 导致极其昂贵，而且经常把包含“见表5.2.1”等关键跳转枢纽的文本打低分并扔进垃圾池，切断了推理线索。
  - **V5 的优势（原生释放）**：不再用 Python 规则阉割大模型的智商。大模型像专家查书一样，先看目录（文件列表），直接去目标书里“扫读”（grep）；如果发现线索被截断，自主调用翻页工具（read_file_range）往上下看。逻辑严密，几乎媲美官方 Code Interpreter 的性能，且成本极低。
- 适用场景：所有查询，只要你的模型支持良好的 Function Calling 能力（如 Kimi、Qwen-Max 等），这是目前效能和成本的最优解。

**版本选择建议：**

**agentic_search.py - 目录增强版本（强烈推荐）**
- 核心优势：
  - 智能目录路由：无需生成正则表达式，直接通过目录定位相关章节
  - 自动配对机制：AI 选中正文章节时，自动补充对应的条文解释章节（反之亦然）
  - 精准章节切片：基于目录边界精确截取，避免无关内容干扰
  - 模糊文件匹配：即使文件名不完全一致也能准确匹配
- 前提条件：需要提供 menu.json 目录文件
- 适用场景：有完整目录结构的规范文档，准确度和性能最优

**版本选择建议：**
- 想要极简、高效、聪明的原生 Agent 体验，且模型支持函数调用 → **V5（强烈推荐）**
- 有完整规范目录且需要绝对严谨的章节防串号 → **agentic_search（推荐补充）**
- 需要在不支持 Tool Calling 的弱模型上运行简单查询 → V2
- （注：V3/V4 作为 Agent 演进的历史参考保留，实际生产中推荐直接使用 V5）

### 基本用法

根据你的需求选择合适的版本：

```cmd
# 有目录文件时强烈推荐（准确度最高）
python agentic_search.py

# 需要精准控制信息质量和召回率
python rg_search_v4.py

# 复杂查询（多表格、多条文交叉引用）
python rg_search_v3.py

# 简单查询（单条文答案）
python rg_search_v2.py

# 基础版本（快速验证）
python rg_search_v1.py
```

### 自定义查询

修改脚本底部的参数：

**V1/V2 版本：**
```python
run_spec_query(
    user_question="基础的宽高比",  # 你的问题
    context_lines=15,              # 上下文扩展行数
    max_matches_per_file=20        # 每个文件最多匹配数
)
```

**V3/V4 版本：**
```python
agent = DocAgenticSearch(
    target_folder='./specs/',      # 规范文件夹路径
    max_iterations=3,              # 最多迭代次数
    context_lines=30               # 智能展卷的最大搜索半径
)
agent.run_query("筏板的最小厚度是多少")
```

### 参数说明

**V1/V2 版本参数：**
- `user_question`: 用户提出的问题（中文）
- `context_lines`: 命中行上下扩展的行数，建议 10-30（清洗格式可用 0-1）
- `max_matches_per_file`: 每个规范文件最多抓取的匹配数，建议 10-20

**V3/V4 版本参数：**
- `user_question`: 用户提出的问题（中文）
- `target_folder`: 规范文件夹路径，默认 './specs/'
- `max_iterations`: 最多迭代次数，建议 2-3（防止过度搜索）
- `context_lines`: 智能展卷的最大搜索半径，建议 20-40（用于规则引擎和 LLM 兜底）

## 程序工作原理

### agentic_search 目录增强版本流程（有目录时强烈推荐）

```
用户问题 → [推理模型]查阅目录树路由 → 自动配对条文解释 → 模糊匹配文件名 → Python智能切片章节 → [推理模型]综合回答
```

核心优势：
- 🎯 智能目录路由：无需生成正则表达式，直接通过目录定位相关章节
- 🔗 自动配对机制：AI 选中正文章节时，自动补充对应的条文解释章节（反之亦然）
- ✂️ 精准章节切片：基于目录边界精确截取，避免无关内容干扰
- 🔍 模糊文件匹配：即使文件名不完全一致也能准确匹配（如"建筑地基基础设计规范"能匹配到"3建筑地基基础设计规范[附条文说明].txt"）
- 📊 准确度极高：通过目录定位 + 条文解释配对，大幅提升答案的完整性和准确性
- ⚡ 性能最优：跳过正则生成和全文检索，直达目标章节

前提条件：
- 需要提供 menu.json 目录文件（格式见 menu.json 示例）
- 文本文件需要有清晰的章节标题结构
- 目录中条文解释章节需使用前缀标记，如 "(条文解释)6.3 筏形基础设计"

### V2 通用优化版本流程（无目录时推荐）

```
用户问题 → [快速模型]生成正则(带自我修复) → ripgrep 检索 → [推理模型]智能初筛 → 精准扩展上下文 → [推理模型]综合回答
```

优势：
- 通用性强，适用于任何文本库
- 无需提供目录文件
- 智能初筛减少噪音

### 四阶段详细步骤（V2 版本）

**阶段1：正则生成与自我修复（快速模型）**
   - 用户输入自然语言问题（如"筏板的最小厚度是多少？"）
   - 使用快速模型（Qwen-30B）分析问题，提取核心实体和属性
   - 生成优化的正则表达式，包含同义词扩展和规范术语转换
   - 自动检测正则语法错误（如括号不匹配），最多重试 3 次自我修复
   - 例如：将"最小厚度"转换为 `(筏板|筏基|筏形基础|底板).*(厚度|板厚).*(不应|不宜|不得|不小于|mm)`

**阶段2：高速全文检索（ripgrep）**
   - 使用 ripgrep（rg.exe）在 specs/ 目录执行正则搜索
   - 支持忽略大小写、限制匹配数等参数
   - 收集所有命中的文件路径、行号和文本内容

**阶段3：Agentic 智能初筛（推理模型）**
   - 将所有命中结果的摘要发送给推理模型（Kimi/Qwen-235B）
   - AI 自动判断哪些位置最可能包含完整答案
   - 精选出最相关的 5-8 个核心锚点，过滤噪音
   - 初筛对准确度影响很大，必须使用强推理模型
   - 大幅减少后续需要扩展的上下文量，提升效率和准确度

**阶段4：精准上下文扩展与综合分析（推理模型）**
   - 仅对筛选后的核心锚点进行上下文扩展（向上下各扩展 N 行）
   - 将精炼后的规范原文片段发送给推理模型
   - 模型基于原文进行深度分析和总结
   - 流式输出答案，实时展示分析过程
   - 答案中包含规范名称、条文号和行号引用

### V1 基础版本流程

```
用户问题 → AI 生成正则 → ripgrep 检索 → 全量上下文扩展 → AI 综合回答
```

基础版本使用单一模型处理所有步骤，对所有命中结果进行上下文扩展。

### 核心技术优势

- **ripgrep**: 使用 Rust 编写的超快文本搜索工具，比传统 grep 快 10-100 倍
- **快慢模型分离**: 快速模型处理简单任务（正则生成），推理模型处理复杂任务（智能初筛、最终分析），平衡成本与效果
- **正则自我修复**: 自动检测和修复语法错误，提高正则生成成功率
- **Agentic 初筛**: 推理模型智能判断相关性，减少 50-80% 的无效上下文，提升准确度
- **上下文窗口**: 自动扩展命中行的上下文，避免信息碎片化
- **流式输出**: 使用 OpenAI API 的 stream 模式，实现打字机效果

## 注意事项

1. 首次运行会自动创建 `specs/` 文件夹
2. 确保 `rg.exe` 与脚本在同一目录（仅 rg_search_v2 需要）
3. 需要配置 `.env` 文件并填入有效的 ModelScope API Key
4. API Key 需要有足够的调用额度
5. 规范文件建议使用 UTF-8 编码
6. 上下文行数过大会增加 token 消耗（仅 rg_search_v2）
7. 如果规范文件已经清洗为一行一条的格式，可以将 `context_lines` 设为 0 或 1（仅 rg_search_v2）
8. agentic_search 需要提供 menu.json 目录文件，但准确度和性能最优，强烈推荐
9. agentic_search 的目录文件中，条文解释章节需使用前缀标记，如 "(条文解释)6.3 筏形基础设计"
10. agentic_search 会自动配对正文和条文解释，无需手动指定
11. rg_search_v2 通用性强，无需目录文件，适用于任何文本库
12. 正则生成失败时会自动重试最多 3 次，如仍失败请尝试换个问法（仅 rg_search_v2）
13. 智能初筛对准确度影响很大，必须使用强推理模型（Kimi/Qwen-235B），不能用快速模型
